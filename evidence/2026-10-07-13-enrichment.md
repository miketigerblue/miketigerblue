# AI enrichment, measured in production

**Observation window:** 7–13 October 2026 UTC  
**Snapshot collected:** 14 October 2026  
**System:** my independent threat intelligence platform

During this seven-day window, the lake retained **1,982 analysis records**, and the enrichment run log recorded **271 runs**, all with completion timestamps. Each analysis in the window had a model ID, prompt version and input hash.

The daily distribution matters. **1,515 records were analysed on 13 October: 76.4% of the week's total.** The daily counts were 134, 120, 103, 11, 3, 96 and 1,515. A weekly average would obscure that concentration.

These aggregates do not establish why the workload was uneven. They do not distinguish a source-volume increase, replay, backfill or another operational change. That would require examining the relevant input timestamps, run metadata and deployment history.

## The engineering behind the measurements

AI enrichment is one stage of a larger system: ingestion, structured analysis, storage, retrieval and reporting. Keeping execution metadata alongside the analysis makes the system easier to inspect as models and prompts change.

The public [tiger-eye implementation](https://github.com/miketigerblue/tiger-eye) documents per-analysis model and prompt identifiers, an input hash, token counts and LLM-call latency, alongside per-run telemetry. Its architecture also documents bounded concurrency, retry handling and transactional persistence of analysis and embeddings.

Those mechanisms support different operational questions:

- **Workload:** how much work was recorded, and when did it concentrate?
- **Execution history:** which model and prompt version are recorded for an analysis?
- **Performance:** what latency did the measured model calls have?
- **Investigation:** which inputs and runs should be examined when output changes?

Field coverage alone does not validate the contents of those fields or make an analysis correct. A separate evaluation against source evidence is needed to assess extraction quality and analytical usefulness.

## Measurement definitions and limits

The [published aggregate data](2026-10-07-13-enrichment.json) contains the values behind the graphic. It was obtained with read-only aggregate queries against the connected lake.

- **Window:** timestamps greater than or equal to `2026-10-07T00:00:00Z` and less than `2026-10-14T00:00:00Z`. Daily buckets use UTC.
- **Analysis cohort:** rows retained in `analysis` at extraction, filtered by `analysed_at`. These are analysis records, not distinct incidents, source publications or verified threats.
- **Provenance-field coverage:** `model_id`, `prompt_version` and `input_hash` are all non-null. The input hashes themselves are not published in this aggregate.
- **Latency:** percentiles of non-null `analysis.latency_ms` across the window, calculated over individual rows. These are recorded LLM-call timings, not ingest-to-report timings or averages of daily percentiles.
- **Runs:** `pipeline_runs` entries selected by `started_at`. A run is counted as completed when `finished_at` is non-null at extraction. This does not mean every run finished before the window ended.
- **Reliability:** the run log describes recorded work cycles. It cannot establish uptime, missed schedules, unrecorded failures, maximum capacity or recovery performance.
- **Scope:** this snapshot describes the connected independent platform. It is not a benchmark of every public repository, and it does not describe an employer's systems.

The useful result is a bounded, inspectable account of one week's processing. Capacity, availability and analytical accuracy each need their own measurements.
